# Issues found against the shared package and the spec

Not fixed here (not owned by the UI). Please decide in the owning phase.

1. **(Resolved, see 13) No asset list endpoint.** Deposit and withdraw take `origin_asset` / `dest_asset` strings but the API has no way to list supported assets, their decimals or address kinds. The UI uses a static provisional list in `src/ui/cash-assets.ts`.
2. **(Resolved, see 15) Deposit / withdraw status vocabulary is undefined.** `status` is a free string. The UI maps several likely words (`PENDING_DEPOSIT`, `PROCESSING`, `SUCCESS`, `EXPIRED`, `REFUNDED`, `FAILED`) in `mapCashStatus()`.
3. **(Resolved, see 14) Mock faucet cooldown is 60 s and the real one is unknown** (OPEN_QUESTIONS #4). The UI starts a local 60 s wait after a claim and otherwise relies on `RATE_LIMIT`.
4. **A merchant treasury (500 coins at the start) limits what a player can sell.** One caravan of spice or silk can easily exceed it, so a sale shows `MERCHANT_BROKE`. The UI caps the quantity to what the merchant can pay and says so, but the economy tuning phase should check that early sales are not frustrating.
5. **Mock state is in memory.** A reload during a journey loses it in mock mode (the shared mock has no persistence). The real server keeps it.
6. **Tick length in the mock is 5 s, the spec says 60 s.** The UI only shows the tick number, never a countdown.
7. **Merchant to portrait mapping is not specified.** `src/ui/game-meta.ts` assumes dasht=golnar, madan=rostam, bandar=nahid, shahr=sohrab.
8. **Login button target.** In real mode the buttons navigate to `/api/auth/signin?provider=...`; the server phase should confirm the Auth.js route or replace `startLogin()` in `src/ui/session.ts`.
9. **Dev login (done).** With `NEXT_PUBLIC_MOCK=0` the login screen probes `GET /api/dev/login` once (404 means off). When it answers 400 the OAuth buttons are replaced by a name box and Play (`POST /api/dev/login`), and Log out calls `/api/dev/logout`. Helpers in `src/ui/session.ts`; walkthrough script `src/ui/shoot/live.mjs` writes `docs/screens/live-*.png`.
10. **`Stall` has no seller display name.** The API gives `seller` as an account id only, and the leaderboard has names without ids, so the stalls screen cannot show who is selling. `sellerLabel()` in `src/ui/stall-math.ts` shortens the id ("Trader 1a2b" for generated accounts, the first label otherwise, "You" for the player). Proposal for `packages/shared`: add `seller_name: string` (the seller's `display_name`) to `Stall` and to the server's `toApiStall`.
11. **The UI cannot tell whether a stall can sell right now.** The contract (D6) refuses `stall_buy` with `NOT_IN_CITY` unless the seller is in the stall's city and not travelling, but `Stall` carries no seller location or journey flag. A buyer only finds out after tapping Buy (the UI then says "The seller is away from this city"). Proposal: add `seller_present: boolean` (or the seller's location and a travelling flag) to `Stall`, so the list can mark such stalls and disable Buy.
12. **Stall rules the mock does not enforce** (`packages/shared/src/mock.ts`): `stallCancel` works from any city and while travelling, there is no 5-stall limit and no 1..1,000,000,000 fils price range, and a stall can be bought while its seller is elsewhere (the mock only has the fixture seller). The UI follows the contract: cancel needs the player in the stall's city and not travelling, at most 5 open stalls, price 0.01 to 10,000,000.00 coins.

## Contract parity (UI side of server item 17)

13. **Cash assets come from `GET /api/tokens` (done).** `ApiClient.tokens()` (shared) returns `{assets: [{id, symbol, chain, decimals}]}`. LiveCash loads it with SWR (loading, error with retry, and empty states), shows "USDC on NEAR" style labels and sends the real `id` as `origin_asset` / `dest_asset`. The address check is chosen from the chain (`near`, `eth`/`base`/`arb`/... as EVM, `sol`, `btc`); any other chain gets a generic "6 to 128 characters, no spaces" check, so a new chain works but with a weaker input check. The mock client returns `MOCK_TOKENS` (the old static list, made-up ids) so the demo and `?live=1` still work. PLAY keeps Cash closed. A long list (1Click has many tokens) is one plain select for now; a search box would help if it grows.
14. **Faucet follows the contract in the real game (done).** `ui/faucet-rules.ts`: `faucetWorthFils` = coins + inventory + goods in the player's own stalls (from `world.stalls`, base prices) + cargo of an IN_TRANSIT journey (an ARRIVED, unclaimed journey is not counted, as in the contract); Claim is offered only below 5,000 fils. The wait is 3,600 s. The server never says when the last claim was, so the UI remembers its own claim time per account in localStorage (`caravan.faucet.until.<account>`); after a RATE_LIMIT with no memory it assumes a full hour and says "about an hour" (upper bound). Messages: RATE_LIMIT "Available again in about an hour.", BAD_REQUEST "You still own too much to claim...". The demo (`NEXT_PUBLIC_MOCK=1`) keeps its rule: 60 s wait, no wealth limit, the old banner rule. Proposal for the server: return the next claim time (or `faucet_cooldown_seconds` and last claim) in `Player` or the RATE_LIMIT error so the UI need not guess; and `faucet_max_balance_fils` / `faucet_cooldown_seconds` in `/api/state` so the constants are not duplicated (`FAUCET_MAX_WORTH_FILS`, `FAUCET_COOLDOWN_REAL_SEC`).
15. **Withdraw limits and status words (done).** The withdraw button is off below `PARAMS.MIN_WITHDRAW_FILS` (10 coins) with an inline message; the server's reasons for BAD_REQUEST (withdrawal already in progress, UTC-day cap with refunds counted, minimum, unsupported asset, deposit limit) are shown instead of the generic text (`cashErrorText` in `ui/cash-rules.ts`, matched on the server message; other BAD_REQUESTs keep the generic text because contract panics are already reduced to "That action is not allowed right now."). `mapCashStatus` now covers every status the server stores (deposits PENDING, CREDITING, CREDITED, EXPIRED, FAILED; withdrawals RESERVED, REQUESTED, SENDING, SENT, FINALIZING, DONE, REFUNDED, FAILED, CANCELLED). SENT is "processing" (it used to count as done, but a refund is still possible). A FAILED deposit also stores a provider refund and a deposit that waits for a manual refund, so the text no longer says "Nothing was credited" alone: no coins were added, and the money is refunded or returned by hand. Not distinguishable from the API: a provider-refunded deposit and one stuck for manual refund both read FAILED; proposal: a separate `REFUNDED` deposit status (or a `refund` flag) from the cron when the provider reports REFUNDED. Note: `POST /api/withdraw` answers only REQUESTED and there is no withdrawal status endpoint, so the UI cannot show later states (SENT, DONE, REFUNDED); the balance is the only signal. Proposal: `GET /api/withdraw/status`.
